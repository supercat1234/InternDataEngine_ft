# 批量布局长时间停留：重复 IK 搜索与预算修复

2026-10-30 的 13:18:51 批次再次复现：第一条成功后，第 2~4 条布局分别耗时约 5、10、10 分钟，最终均未找到完整抓放链。卡住的外观来自主线程持续做规划，不是等待数据保存。此前只诊断了该性能问题，没有实际加入总预算；本次完成实现。

## 修改

1. 灵活放置模式先求预放置、落盘两个端点，只为二者都通过的候选生成空夹爪撤退姿态。此前每次都求 216×7 个撤退目标，即使放置点已经不可达。
2. 同一碰撞世界、附加物体版本、精确目标集合内，缓存 IK 的全部返回分支和有效标记。抬升起点改变时重新评分选择分支，无须重做同一批优化。改变世界或附加物体后自动失效。搜索未成功的结果只表示这次有限搜索未找到解，不作为数学上的无解证明；预算内的缓存会减少重复随机重启，因此不承诺提高解的完备性。
3. 初始整段搜索共享 45 秒预算，不能由候选或路径段重新计时。实抓后放置重规划独立使用 20 秒，执行起点偏移造成的单段刷新使用 10 秒。超时成为本布局的正常失败，清理虚拟附加几何，交给原流程处理下一个布局或 strict 重试。仅捕获明确的预算异常，CUDA OOM、写入异常等不会被当作正常超时吞掉。
4. 在每批 IK 前后、每段路径和候选之间检查时间。后备 MotionGen 调用的 timeout 不超过剩余预算。每 5 秒打印阶段、已用时间、剩余时间、实际求解目标数和缓存命中数。

碰撞、关节限位、抓取接触、最终支撑与稳定判据保持原要求。杯盘范围、机器人位置和抓取候选未改变。

## 设置

在 `local_configs/cup_plate_desk/task.yaml` 的 Pick 段配置：

```yaml
chain_planning_timeout_s: 45.0
chain_place_timeout_s: 20.0
chain_refresh_timeout_s: 10.0
chain_progress_interval_s: 5.0
```

预算按规划阶段计时，不包括 Isaac 启动、场景重置/落稳、正常轨迹执行或数据编码保存。采用协作式检查，不会强行终止运行中的 CUDA 调用；单次 GPU 调用、球拟合或系统调度可能造成超出少量时间。它不是进程级看门狗，不能替代处理驱动挂起。

`strict_mode=false` 时，超时布局计入尝试次数，不保存成功样本。`strict_mode=true` 时，超时后仍按原规则重新采样；`MAX_RETRIES=-1` 依然允许无限次重试，所以整批总时长仍可能很长，但单个初始规划搜索有预算限制。

修改只对重新启动的实例生效；无需改变原单实例或并行运行命令。
